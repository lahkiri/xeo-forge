# v1.13.0 — A Loop Worthy of a Strong Model

## Summary

v1.12.0 proved the governance layer; this release makes the agent loop itself
worthy of a frontier model. The audit question was blunt: *if a user configures
an Opus-class model and trusts the product with real work, will the loop let
the model perform — or fight it?*

The answer was: fight it, in three specific ways. All three are fixed, each
pinned by tests, and none of them weakens a single guarantee for weaker models.

## Guard profiles: the loop adapts to the model

The stagnation and read-loop thresholds were calibrated against models that
genuinely loop — same call, same failure, no adaptation. A frontier model's
legitimate work looks different: it studies a large codebase before touching
anything, and it runs iterated fix-test loops that are the *shape of progress*,
not the absence of it.

`GUARD_PROFILES` in `lib/agent/guards.ts` introduces two tiers:

| | stagnation threshold | consecutive reads |
|---|---|---|
| **standard** (unchanged) | 3 | 6 |
| **strong** (Opus, Claude 4+, GPT-5+, o-series, Gemini 2+ Pro, DeepSeek R/V3, Grok 3+) | 6 | 15 |

Detection is a coarse heuristic on the configured model id — no schema change,
no admin action. A model that is misclassified degrades to the stricter
profile, never to something unchecked. Existing deployments keep the exact
historical numbers.

## Stagnation fingerprints now read the world

The old stagnation fingerprint was a hash of tool names and argument prefixes.
A model fixing a failing test runs the same command repeatedly — identical
name, identical arguments — while the *result* changes every round as the fix
converges. The old fingerprint counted that as repetition and, given enough
rounds, killed a productive run.

The fingerprint now includes a 120-character prefix of each tool observation,
at all three signature call sites (native tool-calling loop, fallback execute
path, fallback todo_update path). The rule it enforces is now precise:

- same call, same world → stuck → escalate
- same call, different world → progress → let it work

For `code_execute` the observation begins with the exit code, so even
`exit=1` → `exit=0` flips the fingerprint.

## The summary gate obeys the language it was told to use 🐛

A real defect, found by reading two rules that contradicted each other. The
system prompt orders the model to respond in the user's language (LANGUAGE
AFFINITY). The `task_complete` gate accepted only the English words
*assumption*, *decision*, *issue*, *workaround*. A perfectly structured Arabic
summary was rejected, retried, and could fail the run — the product punishing
the model for obeying the product.

`validateSummarySections` now lives in `guards.ts` beside every other
behavioral check (one implementation, AGENTS.md §5.5) and accepts the four
engineering-memory sections in English, Arabic, French, Spanish, Russian, and
Chinese. The prompt contract was sharpened to match: the four lists carry
their **English titles** (machine-checkable, deterministic) while the **content**
is written in the user's language. Pinned by a behavioral battery covering all
five languages plus partial-credit missing-section naming.

## Honest boundaries

- Every threshold change is verified by unit tests against the shipped
  modules — not by a live model run. The loop is now *ready* for a frontier
  model; proving it end-to-end with real Opus-class runs is the owner's flame
  test, and the numbers above will be tuned by its evidence, not by optimism.
- `standard` deployments see zero behavioral change beyond the language fix:
  same thresholds, same nudges, same termination rules.
- The dead `STAGNATION_THRESHOLD` module constant was removed; the live loop
  reads its profile. Nothing else in the loop was rewritten — its structure
  (single dispatch chokepoint, one event path, semantic termination,
  evidence-based verification) was already right.
