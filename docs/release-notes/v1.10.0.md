# v1.10.0 — Persistent Context

## Summary

v1.10.0 is the release where the agent gets more useful over time without
becoming a black box. Memory, instructions, and runtime state all became
inspectable and revocable.

Zero new tables. `agent_memories`, `agent_instructions`, `agent_profiles`, and
`agent_skills` already existed with every column this release needed — what was
missing was the approval path, the visibility, and the honest runtime reporting.

## Memory the user controls

The agent proposed memory candidates at completion and wrote them as
`status='proposed'`, but there was no way to approve one, so nothing ever
reached run context.

- `POST /api/tasks/:id/memory` is the only transition from proposed to approved.
  It is idempotent — a second decision on the same candidate returns 409 rather
  than silently re-approving — and it emits a `memory_decision` event so both
  approval and rejection are auditable.
- `GET` returns pending candidates and active memories; `DELETE` forgets one.
- The Work surface has a **Memory** tab (`Cmd+5`) with a badge counting pending
  decisions, so a proposal is never silently dropped. Each candidate shows its
  content, kind, scope, and confidence, with **Keep**, **Edit**, and **Reject**.
- Approved memories are listed with a `forget` action.

`getActiveAgentMemories()` filters on `status='active'`, so a proposed memory is
structurally incapable of reaching a run. That is the guarantee, not a promise.

## Injection is visible

When approved memories or instructions are compiled into a run, the loop emits a
`context_layers` event naming exactly which ones. Memory that acts invisibly is
the failure mode this feature exists to prevent.

## Context Inspector

The new **Context** tab answers the question every agent user actually has: what
instructions reached the model, and why?

Every layer resolves to one of four states with a reason and a token estimate:

| State | Meaning |
|---|---|
| in prompt | injected verbatim, possibly clamped |
| withheld | deliberately excluded — disabled, awaiting approval, expired, out of scope |
| overridden | a more specific layer replaced it |
| deduped | byte-identical content already injected once |

It also reports what share of the system prompt is your context versus platform
policy, so a bloated instruction set is visible before it crowds out the task.

**It cannot lie.** `resolveContext()` in `lib/agent/context-pack.ts` is now the
single resolution pass (AGENTS.md rule 1). `compileAgentContext()` renders the
prompt from it for the agent loop, and `describeEffectiveContext()` reports it to
the inspector. Both read the same resolution, so the inspector cannot claim a
layer the model did not receive — and a test asserts that every active layer the
inspector reports exists as active in the injected resolution.

Detection is deterministic: scope specificity, disabled flags, approval status,
expiry, duplicate content, and character-budget clamping. Xeo does **not** use a
model to guess whether two instructions disagree semantically, and does not claim
to.

## Truthful runtime states

`thinking…` is gone. `lib/agent/runtime-state.ts` derives the visible state from
the event stream — the last event type, its payload, and how long ago it arrived:

`idle` · `queued` · `connecting` · `reading_context` · `using_tool` ·
`receiving` · `waiting_for_provider` · `retrying` · `compacting` · `completed` ·
`failed`

Chat and Work now show the actual operation with elapsed time — "Reading project
context: auth/session.ts 0:13" instead of an animation. After 10 seconds of
provider silence the state becomes `waiting_for_provider` and says so, rather
than leaving a spinner to imply progress that is not happening. A retry reports
its attempt number and reason.

The server's task status stays authoritative for terminal state; the UI never
invents completion.

## CI on every push

`.github/workflows/ci.yml` runs typecheck, lint, tests, `git diff --check`,
browser smoke, `go vet`, `go test`, and the production build on every push and
pull request to `master`.

This gap caused the v1.9.0 release failure: a route rename broke the desktop
smoke test and nothing caught it until tag time, because the only workflow
triggered on tags. Now `master` cannot go red between releases.

- The layout section lists `context-pack`, `runtime-state`, and the two new

## Verification

- `npm run typecheck` — clean
- `npm run lint` — clean, zero warnings
- `npm test` — 224 tests passing, up from 207 (17 new: 12 context resolution, 5
  runtime state — plus the runtime-state file's full stall-threshold coverage)
- `npm run build` — compiled successfully

New tests exercise the shipped modules directly. `test/context-pack.test.ts`
runs against a real schema and asserts the approval gate, override precedence,
and inspector-versus-loop agreement.

## Compatibility

Backward compatible. No schema migration. Existing memories, instructions,
profiles, skills, and task history are unchanged. A memory previously created as
`active` through Context Studio keeps working; only agent-proposed candidates go
through the new approval path.
