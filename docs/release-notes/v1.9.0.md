# v1.9.0 — Chat Is Chat, Work Is Work

## Summary

v1.9.0 rebuilds the interface around the product contract. Chat and Work were
previously the same screen with a mode toggle, which meant a conversation
rendered approval controls it could never use and a governed run buried its
approval gate at the bottom of a scroll. They are now separate surfaces with
separate layouts, and the governance the backend already enforced is finally
visible.

No backend, schema, or API change. This is entirely the interface layer.

## Chat is conversation only

`/chat` is a conversation app: thread list, centered message column, composer
pinned to the bottom, `Enter` to send and `Shift+Enter` for a newline.

It deliberately has **no** tabs, phase indicator, workspace browser, preview
pane, approval controls, or credit meter. Chat cannot plan and cannot write, so
nothing in the layout implies that it can. A "Switch to Work" action promotes a
thread when the conversation turns into real work.

## Work leads with governance

`/work` is a workbench: run list, a center pane with four tabs (Run, Project,
Preview, Context), and a **governance rail** that surfaces what the backend was
already enforcing:

- Current state, mode, and classified intent.
- **Authority for this run** — whether writing files and running commands are
  allowed or locked right now, and whether a plan is frozen.
- The project boundary path the run is confined to.
- Credits spent, action count, live context meter with token detail.
- The agent's checklist and every file it changed.

The Work intake states the authority grant *before* the run exists, so a user is
never surprised by agency they did not knowingly grant.

## The approval gate is now the centerpiece

A plan awaiting approval takes the entire pane, renders readably, and offers two
unambiguous actions: **Approve and build**, or **Request changes** with a reason.
It was previously a pair of small buttons near the end of a 922-line component.

The 30-second decision gate is a full-width band with a live countdown that turns
red under ten seconds, and copy stating that expiry runs nothing rather than
defaulting to execution — matching what the server actually does.

The tool ledger reads like an audit log: one row per action, colour-coded by
impact class (read / write / execute / network), with arguments, timing, success
state, and expandable output.

## Keyboard-first

- `Cmd/Ctrl+K` — command palette with subsequence matching (`nw` finds "New Work"),
  arrow and Enter navigation, grouped results.
- `Cmd+Shift+C` new chat, `Cmd+Shift+W` new work, `Cmd+,` Control Center.
- `Cmd+1..4` switch Work panes, `Cmd+Enter` submit, `Esc` dismiss.

Bare-key bindings are suppressed while a text field has focus, so shortcuts never
swallow composer input.

## Design system

`components/ui.tsx` grew from 5 primitives to a real library: Button (five
variants, loading state), IconButton, Card, Panel, PanelHeader, Input, Textarea,
Select, Badge, StatusBadge, Tabs, KeyHint, Dialog, Toast provider, Alert, Meter,
Metric, EmptyState, Skeleton, Divider.

One `STATUS_TONE` map now drives every status colour in the app. Four divergent
inline ternaries previously decided it per file — the reason the old UI looked
inconsistent in its details.

## Added

- Role and workflow selection on the Work intake. `agent_profiles` and
  `agent_skills` were persisted, validated, and compiled into run context, but
  had no selector — so both were always `null`.
- Credits spent and context token counts are rendered. Both were streamed on
  every event into state that nothing displayed.
- `lib/markdown.ts` — extracted so Chat and Work render assistant output
  identically instead of one carrying a private copy (rule 1).

## Removed

- `app/dashboard/DashboardClient.tsx` (226 lines) and
  `app/tasks/[id]/TaskClient.tsx` (922 lines).
- `/dashboard` and `/tasks/:id` are now redirects. Old links, bookmarks, and
  exported audit trails keep working: a task routes to Chat or Work based on its
  persisted `mode`.

## Documentation honesty

`code_execute` was described as a "sandbox". It is `child_process.exec` with an
environment whitelist, realpath-checked path boundaries, and a command blocklist.
That is meaningful defence-in-depth, but it is **not** OS-level isolation — there
are no namespaces, no seccomp, no container, no separate uid — and indirection
(writing a script, then running it) defeats string-pattern checks.

README and AGENTS.md now say **restricted host execution** and state the limit.
Overstating a security boundary is the one documentation error that can actually
harm a user.

Backward compatible. No schema migration. Existing tasks, conversation history,
uploads, memories, roles, and workflows are unchanged and reachable — the router
