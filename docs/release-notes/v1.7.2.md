# Xeo Forge v1.7.2 — Provider Reliability Hotfix

## Summary

This patch fixes a provider reliability blocker affecting local model connection tests and agent conversations, especially with reasoning and free-tier models such as OpenCode Zen's `deepseek-v4-flash-free`.

## Fixed

- Replaced the invalid `max_tokens=1` Test connection payload with a safe 256-token completion budget.
- Normalized saved and environment-provided `max_tokens` values to a practical range of 256–200,000 tokens.
- Normalized OpenAI-compatible base URLs by removing trailing slashes before creating the SDK client.
- Disabled hidden OpenAI SDK retries so Xeo's visible, bounded exponential backoff remains the single retry path.
- Applied the same no-hidden-retry behavior to context compaction requests.
- Improved HTTP 429 messaging to distinguish an accepted provider connection from a temporarily exhausted completion quota.
- Surfaces a provider-supplied `Retry-After` wait hint when available.
- Updated the Local Control Center and SaaS Admin model forms to prevent unusable token limits and explain reasoning-model requirements.
- Added regression coverage for model normalization, 429 classification, retry-after messaging, authentication failures, and network failures.

## Verification

- `npm run typecheck`
- `npm test -- --run`
- `npm run build`
- `npm run desktop:smoke`
- `npm run browser:smoke`

All checks passed. The first full-test failure was an environment-only `better-sqlite3` Node ABI mismatch; rebuilding the native dependency for the active Node runtime resolved it without changing application behavior.

## Configuration example

```text
Base URL: https://opencode.ai/zen/v1
Model ID: deepseek-v4-flash-free
Max output tokens: 256 or higher
```

A valid key can still receive HTTP 429 when the upstream model quota is temporarily exhausted. Xeo now reports that condition explicitly instead of presenting it as an ambiguous provider failure.
