# خطة Xeo Forge: Local-First Workbench vNext

## الهدف

تطوير Xeo Forge من واجهة Local Workbench مبنية حول مساري Chat وTask إلى **Control Plane for Agentic Work** أكثر وضوحًا وأمانًا، بحيث يفهم الوكيل نية المستخدم قبل تشغيل التخطيط، ويتيح قرارًا سريعًا ومدققًا بين التنفيذ المباشر والتخطيط، ويدمج متصفح المستخدم اختياريًا بخصوصية وصلاحيات صريحة، ويستقبل تحديثات Windows هوائيًا دون تنزيل installer يدويًا في كل إصدار.

النتيجة المستهدفة ليست تجاوز بوابة الموافقة، بل جعلها **مرنة حسب نية المستخدم**: الرسائل العادية لا تُحوّل إلى خطة، والطلبات الصريحة للتخطيط تبدأ التخطيط فورًا، والطلبات الصريحة للتنفيذ المباشر تعرض بطاقة قرار قصيرة قبل أي تغيير.

## قرارات المنتج الأساسية

| الحالة | السلوك المقترح | هل يبدأ تشغيل الوكيل؟ |
|---|---|---|
| رسالة عادية أو سؤال عام داخل Work | رد محادثي عادي، من دون خطة أو تنفيذ | نعم، Chat response فقط |
| طلب صريح مثل «خطط لبناء…» | يبدأ Planning مباشرة ويعرض خطة منظمة للموافقة | نعم، Planning |
| طلب صريح مثل «نفّذ هذا» بلا خطة مسبقة | تظهر بطاقة قرار: «تخطيط أولًا» أو «تنفيذ مباشر» مع عداد 30 ثانية | لا قبل اختيار المستخدم |
| نية غير مكتملة أو خيارات متعارضة | تظهر أسئلة أو خيارات قصيرة، ولا يبدأ تنفيذًا تخمينيًا | لا قبل الإجابة |
| طلب حساس أو غير قابل للعكس | يتطلب تأكيدًا خاصًا حتى لو اختار المستخدم التنفيذ المباشر | لا قبل التأكيد |
| انتهاء عداد 30 ثانية دون اختيار | يُطبّق الخيار الآمن: التخطيط أولًا أو إبقاء الطلب بانتظار المستخدم، ولا يُنفذ مباشرة | لا تنفيذ تلقائي |

سيُعامل اختيار «تنفيذ مباشر» كـ **موافقة صريحة على تنفيذ طلب المستخدم كما هو**، ويُحفظ كقرار تدقيقي مع نطاق الطلب والأدوات المسموح بها. وللحفاظ على قاعدة التنفيذ القابلة للتدقيق، سيُنشأ execution brief immutable يمثل طلب المستخدم وحدود التنفيذ، ثم يعمل Build عليه؛ لن يسمح هذا المسار للوكيل بإعادة كتابة هدفه أو توسيع نطاقه أثناء التنفيذ.

## المرحلة الأولى: تثبيت العقد المعماري والسياسات

قبل كتابة الكود، سيتم تحديث العقد المعماري في `AGENTS.md` ووثائق Desktop ليعكس أن `chat` و`planning` و`build` هي حالات تشغيل داخل واجهتي `Chat` و`Work`، وأن Work يملك طبقة intent/decision قبل الوصول إلى planning أو build. سيتم تحديد مصدر واحد لكل قرار، وعدم إضافة جداول أو حالات لا يمر بها مسار كامل من UI إلى API إلى runner إلى persistence.

سيُعرّف نموذج قرار موحد، مثل `intent_decision`, يحتوي على نوع النية، درجة الثقة، سبب العرض، الخيارات، تاريخ الانتهاء، الخيار الافتراضي الآمن، وحالة القرار. سيُحفظ القرار في قاعدة البيانات أو ضمن سجل task/event canonical، مع endpoint idempotent لا يقبل اختيارًا بعد انتهاء المهلة أو بعد اختيار سابق. لن يُعتمد على مؤقت الواجهة وحده.

كما سيتم تحديد مصفوفة صلاحيات موحدة للأدوات: القراءة، تعديل الملفات، تنفيذ الكود، تشغيل preview، والتصفح. هذه المصفوفة ستُستخدم في التخطيط، والتنفيذ المباشر، وChat، ولن تكون مجرد تعليمات في system prompt؛ ستُفرض عند dispatch كما تُفرض حاليًا قيود Planning.

## المرحلة الثانية: طبقة فهم النية وقرار Work

سيتم بناء intent router صغير ومحدد لا يبدأ بالتخطيط لكل رسالة. سيبدأ بتحليل حتمي سريع لإشارات مثل: التخطيط، التنفيذ، الإصلاح، الإنشاء، الفحص، السؤال، الشرح، أو طلب الاختيار. إذا كانت النتيجة واضحة، يُستخدم المسار المناسب بلا استدعاء إضافي. وإذا كانت النية ملتبسة، يمكن استخدام النموذج المضبوط لاستخراج تصنيف منظم فقط، مع إبقاء القرار النهائي محكومًا بسياسة الخادم.

سيكون التصنيف قابلًا للتفسير في السجل، مثل: `conversation`, `explicit_plan`, `direct_execution`, `clarification_needed`, `sensitive_action`. لن يسمح التصنيف وحده بتنفيذ تغيير؛ هو يقرر أي بطاقة أو مسار يظهر للمستخدم.

### بطاقة التنفيذ المباشر

عند اكتشاف طلب مباشر بلا خطة سابقة، سيظهر في thread عنصر واضح وغير مزعج يتضمن ملخصًا قصيرًا لما فهمه الوكيل، النطاق المتوقع، الأدوات التي قد يستخدمها، وعدّادًا مرئيًا لمدة 30 ثانية. ستحتوي البطاقة على زرين:

1. **تنفيذ مباشر**: يبدأ المسار المباشر بعد تسجيل اختيار المستخدم.
2. **تخطيط أولًا**: ينشئ Planning task ويعرض الخطة المعتادة للموافقة أو الرفض.

الاختيار سيكون متاحًا أيضًا بلوحة المفاتيح، وسيكون endpoint القرار idempotent. عند انتهاء العداد، سيصبح القرار `expired` ويُطبق الخيار الآمن؛ لن يتحول الطلب إلى تنفيذ تلقائي. ستظهر للمستخدم نتيجة انتهاء المهلة مع إمكانية اختيار مسار جديد بدل فقدان الطلب.

### أسئلة التوضيح والخيارات

عندما يحتاج الوكيل إلى معرفة ما يريده المستخدم فعليًا، سيعرض `ClarificationCard` تحتوي على سؤالًا واحدًا أو عددًا صغيرًا من الخيارات، مع إمكانية كتابة إجابة حرة. لن تُدفن الأسئلة داخل نص طويل، ولن يبدأ الوكيل تنفيذًا تخمينيًا قبل وصول الإجابة. ستُحفظ الإجابة في المحادثة وتُعاد إلى intent router، مع منع الدوران المتكرر عبر حد لمحاولات التوضيح وإظهار خيار «نفّذ بأفضل افتراض آمن» عندما يكون ذلك مناسبًا.

## المرحلة الثالثة: تحسين التخطيط والقبول والرفض

سيُعاد تصميم plan review ليعرض للمستخدم ما يحتاج إلى قرار فعلي بدل عرض نص طويل فقط. سيشمل العرض الهدف، ما الذي سيُقرأ، ما الذي سيُعدل، الأوامر أو الأدوات المحتملة، الملفات أو المجلدات المتأثرة، المخاطر، واختبارات التحقق. سيُفرّق بصريًا بين حقائق اكتشفها الوكيل وبين افتراضات تحتاج إلى تأكيد.

سيتم توفير إجراءات واضحة هي: **Approve and run**، **Reject with reason**، **Ask for revision**، و**Edit constraints**. الرفض لن يكون مجرد إنهاء غامض؛ سيعود إلى المحادثة برسالة منظمة تحفظ سبب الرفض وتمنح الوكيل سياقًا لإعادة التخطيط. الموافقة ستثبت snapshot غير قابل للتعديل، وتمنع double approval، وتعرض للمستخدم بالضبط ما تم اعتماده.

سيُحسن Work timeline ليُظهر حالات مفهومة: conversation، waiting for choice، clarifying، planning، awaiting approval، executing، needs input، completed، failed. لن تظهر أزرار Plan أو Approve أو Build عندما لا تكون ذات صلة بالحالة.

## المرحلة الرابعة: متصفح المستخدم المحلي الاختياري

### البنية المقترحة

سيتم فصل القدرة عن منطق Next.js عبر **Browser Bridge محلي**. الخيار المفضل هو إضافة متصفح Manifest V3 اختيارية للمستخدم، تتصل بتطبيق Xeo Forge عبر قناة localhost محمية برمز جلسة قصير العمر أو native messaging. يبقى المتصفح الشخصي والمتصفح وملفات تعريف المستخدم تحت سيطرته، ولا تُرسل الجلسات أو كلمات المرور أو cookies إلى الخادم.

سيكون فتح المتصفح أو استخدام التبويب النشط قرارًا صريحًا من المستخدم، مع مؤشرات في الواجهة تبين: المتصفح متصل أو غير متصل، التبويب الحالي، المجال، ونوع الصلاحية. لن يتم اعتماد تحكم شامل في ملف تعريف Chrome عبر CDP كمسار افتراضي؛ هذا أكثر خطورة ويصعب عزله عن كلمات المرور والجلسات الشخصية.

### أدوات المتصفح وصلاحياتها

سيتم إدخال أدوات منفصلة في طبقة `lib/agent/tools.ts`، مثل فتح رابط، قراءة الصفحة، أخذ لقطة، البحث في الصفحة، النقر، الكتابة، والانتظار. ستُفرض الصلاحيات عند dispatch لا عبر prompt فقط.

| مستوى الصلاحية | أمثلة | السياسة الافتراضية |
|---|---|---|
| Read | قراءة DOM، عنوان الصفحة، النص المرئي، screenshot | مسموح بعد تفعيل جلسة المتصفح |
| Navigate | فتح URL أو بحث | مسموح ضمن session/domain policy |
| Interact | click، type في حقول غير حساسة | يتطلب تفعيلًا واضحًا للجلسة |
| Submit | إرسال نموذج، نشر، شراء، حذف، تسجيل دخول | تأكيد منفصل قبل كل فعل حساس |
| Download/Upload | تنزيل أو رفع ملفات | مقيد بالمجال والمسار وتأكيد المستخدم |

سيتم دعم allowlist للمجالات، وdenylist للمجالات الحساسة، وحد زمني للجلسة، وزر إيقاف فوري. لن تُقرأ حقول كلمات المرور أو رموز المصادقة، ولن تُعرض قيم cookies أو headers السرية للوكيل. ستُحفظ سجلات الأفعال والنتائج دون حفظ أسرار الصفحة.

### الخصوصية الواقعية

سيُعرض للمستخدم مؤشر واضح أن التحكم محلي، لكن لن تُستخدم عبارة «لا تخرج أي بيانات» بشكل مطلق إذا كان النموذج البعيد مفعّلًا؛ محتوى الصفحة الذي يرسله الوكيل إلى نموذج بعيد قد يغادر الجهاز. لذلك ستضاف أوضاع خصوصية صريحة:

- **Strict Local**: لا يُرسل محتوى المتصفح إلى endpoint بعيد، ويتطلب نموذجًا محليًا متوافقًا أو يمنع Browser Agent.
- **Private with redaction**: يزيل الحقول الحساسة والأنماط المعروفة قبل إرسال مقتطفات محدودة.
- **Connected model**: يسمح للمستخدم بتفعيل نموذج بعيد مع تحذير دائم ومؤشر واضح.

سيكون استخدام المتصفح في Planning read-only، بينما يتبع Work/Direct Execution مصفوفة الصلاحيات وبطاقات التأكيد. وسيُدمج المتصفح مع preview الحالي بحيث يستطيع الوكيل تشغيل مشروع محلي، فتحه في متصفح المستخدم، فحصه بصريًا، ثم اقتراح أو تنفيذ إصلاحات وفق القرار المعتمد.

## المرحلة الخامسة: التحديثات الهوائية لـ Windows

سيتم تحويل حزمة Electron Builder من installer-only إلى update-aware release channel باستخدام `electron-updater` أو مسار مكافئ متوافق مع Electron Builder وGitHub Releases. ستُنشأ metadata اللازمة مثل latest manifest وblockmap ضمن CI، مع إبقاء GitHub Release مصدر الإصدارات الحالية.

سيعمل التحديث بهذه السياسة:

1. يفحص التطبيق وجود تحديث عند بدء التشغيل وبعد فترة دورية قابلة للضبط.
2. لا يقطع جلسة المستخدم ولا يعيد التشغيل قسرًا.
3. يعرض إشعارًا صغيرًا يتضمن الإصدار الحالي والجديد وحجم التنزيل.
4. ينزّل التحديث في الخلفية بعد موافقة المستخدم أو وفق إعداد Auto-download اختياري.
5. يثبت عند إغلاق التطبيق أو عبر زر Restart to update.
6. يحفظ `userData` وقاعدة SQLite وإعدادات المشروع دون تغيير.
7. يعرض فشل التحديث ويوفر fallback واضحًا إلى الإصدار العامل أو تنزيل installer يدوي.

سيُضاف إعداد stable/beta، وتعطيل التحديث مؤقتًا، وسجل حالة التحديث دون إرسال محتوى المشاريع. ستتم مراجعة التوقيع الرقمي وWindows SmartScreen قبل الاعتماد النهائي؛ updater موثوق بلا code signing ليس تجربة إنتاجية مكتملة. لن تُضمّن مفاتيح توقيع أو أسرار نشر داخل المستودع.

سيُعدل workflow بحيث ينتج installer وmetadata وينشرهما عند tag، مع حماية من نشر نسخة ناقصة، وفحص أن الإصدار الموجود في package metadata يطابق tag. سيتم اختبار update feed على قناة تجريبية أولًا، ثم إنتاج release stable بعد نجاح الترقية من نسخة مثبتة سابقة.

## المرحلة السادسة: إعادة بناء UI/UX حول النية لا حول التعقيد

سيُعاد تنظيم الواجهة حول مسارين واضحين في الرأس أو الشريط الجانبي: **Chat** للمحادثة السريعة و**Work** للعمل المنضبط. سيظهر مجلد المشروع الحالي وحالة المتصفح وحالة النموذج في شريط سياق صغير، بينما تُنقل التفاصيل مثل timeline وcontext وpreview إلى panels أو tabs عند الحاجة بدل عرضها دائمًا.

سيتم اعتماد نظام بصري ثابت للحالات، وبطاقات قرار قصيرة، وempty states مفيدة، ونسخ نصية تشرح لماذا ظهر التخطيط أو لماذا يحتاج الوكيل إلى إجابة. سيُراعى keyboard navigation، focus management، responsive layout، و`prefers-reduced-motion`. سيتم إزالة الأزرار المكررة والخيارات التي لا تنطبق على الحالة الحالية.

سيكون للرسائل العادية مسار سريع لا يعرض خطة، بينما ستظهر بطاقة القرار فقط عندما تكون هناك نية تنفيذ أو غموض حقيقي. وسيستطيع المستخدم فتح «لماذا سألني الوكيل؟» لرؤية سبب مختصر ومفهوم دون كشف chain-of-thought.

## المرحلة السابعة: التنفيذ المرحلي على master

سيتم التنفيذ على `master` مباشرة وفق طلب المشروع، لكن على commits صغيرة قابلة للمراجعة والرجوع، مع عدم إنشاء فروع أو Pull Requests. الترتيب المقترح هو:

| الإصدار المرحلي | النطاق | معيار الخروج |
|---|---|---|
| A | intent router، decision cards، 30-second safe timeout | لا يوجد planning للرسائل العادية، وجميع حالات القرار idempotent |
| B | improved plan review، reject/revise، direct execution brief | approval/rejection والطلبات المباشرة قابلة للتدقيق |
| C | updater feed وواجهة حالة التحديث | ترقية نسخة مثبتة سابقة دون فقدان userData |
| D | local browser bridge read-only | فتح وقراءة screenshot لموقع عام وlocalhost مع إيقاف فوري |
| E | browser interactions and sensitive-action confirmations | كل submit/delete/login/payment يحتاج تأكيدًا منفصلًا |
| F | UI/UX consolidation and Windows release | smoke وE2E وinstaller/update acceptance كلها ناجحة |

لن يتم دمج Browser write actions أو auto-update production في نفس commit مع intent router؛ كل قدرة ستملك اختبارًا مستقلًا ومسار rollback واضحًا.

## خطة الاختبار

سيتم توسيع الاختبارات الحالية لتشمل unit tests لتصنيف النية، أولوية التصنيفات، توليد الخيارات، انتهاء 30 ثانية، الخيار الافتراضي الآمن، idempotency، ورفض القرارات المتأخرة. وستضاف اختبارات API وقاعدة بيانات للقرار، direct execution brief، plan revision، permission scopes، وسجل التدقيق.

سيتم تشغيل اختبارات تكامل للسيناريوهات التالية: رسالة عادية داخل Work، طلب صريح للتخطيط، طلب تنفيذ مباشر واختيار كل زر، انتهاء المهلة، إجابة clarification، رفض خطة مع سبب، إعادة تخطيط، تنفيذ مباشر لطلب آمن، محاولة فعل حساس، وعدم وجود نموذج AI.

سيتم إنشاء desktop smoke جديد يختبر update state عبر feed تجريبي، عدم فقدان `userData`، ظهور update banner، ومتابعة restart. كما سيُختبر Browser Bridge في بيئة محلية مع تبويب test fixture، DOM read، screenshot، localhost preview، domain restriction، permission denial، وإيقاف الجلسة. لن يُستخدم حساب المستخدم الحقيقي أو تبويباته الحساسة في الاختبارات.

قبل كل push ستبقى بوابة التحقق: `npm run typecheck && npm test -- --run && npm run build && git diff --check`. وقبل كل Windows release سيضاف `npm run desktop:smoke` واختبار installer/update من إصدار سابق، ثم فحص artifact وmetadata والتوقيع إن توفر.

## الافتراضات والمخاطر المفتوحة

الافتراض الحالي أن Work هو واجهة نية وإدارة، بينما تبقى `chat|planning|build` حالات تشغيل داخلية لتقليل migration غير الضروري. ويمكن لاحقًا تسمية `build` داخليًا باسم execution دون تغيير تجربة المستخدم.

الخطر الأكبر هو أن «محلي» لا يعني تلقائيًا أن محتوى الصفحة لا يغادر الجهاز إذا كان النموذج بعيدًا؛ لذلك ستظهر الخصوصية كإعداد قابل للفهم، وسيُمنع Strict Local عند عدم وجود نموذج محلي مناسب بدل تقديم وعد غير صحيح.

المتصفح الشخصي يتطلب تثبيت إضافة أو companion محلي. سيُتعامل مع ذلك كاختيار صريح للمستخدم، مع fallback مفيد: Preview المحلي الحالي وفتح الروابط في المتصفح الافتراضي دون تحكم آلي إذا لم تُثبت الإضافة.

التحديثات الهوائية تحتاج قناة نشر وmetadata وتوقيعًا موثوقًا. سيبقى installer اليدوي متاحًا كخطة إنقاذ، ولن يُفعل التثبيت الصامت أو إعادة التشغيل القسري. وإذا تعذر code signing في المرحلة الأولى، سيُعلن ذلك بوضوح ويُطلق updater كتجريبي قبل وصفه كحل إنتاجي نهائي.

لا تشمل هذه الخطة الذاكرة الدائمة التي تتعلم تلقائيًا دون موافقة؛ أي memory candidates ستبقى user-reviewable كما هو التصميم الحالي، حتى لا تتحول تفضيلات أو صلاحيات مستنتجة إلى سلوك غير قابل للتدقيق.
