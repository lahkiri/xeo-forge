# OTA Bootstrap Protocol

## Purpose

`v1.3.0` was published before the desktop updater was bundled. Its installed binary cannot discover or install later releases automatically. `v1.3.1` is therefore reserved as a **manual OTA Bootstrap**: it adds the updater and its local continuity marker, but it does not claim that the broader v1.4.0 product scope is complete.

Browser Bridge, browser permissions, domain allowlists, sensitive-action confirmations, clarification cards, Strict Local, and redaction are intentionally outside this change.

## Local-only update states

The updater exposes only the following renderer-visible states:

| State | Meaning | Persistence |
|---|---|---|
| `idle` | No update operation is active | `userData/update-state.json` |
| `checking` | The packaged app is checking the configured GitHub feed | `userData/update-state.json` |
| `available` | A newer compatible release was found | `userData/update-state.json` |
| `downloading` | The user explicitly approved the download | `userData/update-state.json` |
| `downloaded` | The update is ready for restart | `userData/update-state.json` |
| `installing` | The app recorded an install marker immediately before restart | `userData/update-state.json` |
| `success` | On restart, the current version matches the requested version | `userData/update-state.json` |
| `error` | The feed, download, install, or continuity check failed | `userData/update-state.json` |

No telemetry endpoint, analytics event, or remote success callback is used. The state file is local to Electron `app.getPath('userData')`, alongside the existing `data/xeo.db` and `project.json` files.

## Bootstrap release contract

The first release that contains the updater must be installed manually over the existing v1.3.0 installation. It should be published only after the ordinary application gates pass. The GitHub release must include the NSIS installer, `latest.yml`, and the Windows blockmap generated by electron-builder.

The bootstrap release is not considered to have passed OTA merely because those files exist. Those artifacts prove feed generation, not installed-app continuity.

## Required Windows test

The test operator must use a real Windows machine and record the following checkpoints without deleting the existing application data:

1. Install `Xeo-Forge-Setup-1.3.0-x64.exe` and create durable state: Local Owner, a selected project folder, at least one task/message, and the local model settings required by the installation.
2. Close Xeo Forge, record the installation version, and verify the SQLite path under Electron `userData`.
3. Install the OTA Bootstrap installer over v1.3.0. Re-open the application and verify the version is the bootstrap version and the following values are unchanged: Local Owner identity, task history, model settings, selected project path, and the SQLite file.
4. Publish a newer test release through the same stable feed. Do not reuse the bootstrap tag or overwrite an existing release asset.
5. From the installed bootstrap version, use the in-app update banner to check for the newer release, approve the download, and wait for the `downloaded` state.
6. Choose `Restart to update`. After the application opens, verify the `success` state and compare `app.getVersion()` with the requested version.
7. Verify again that `userData/data/xeo.db`, Local Owner, model settings, task history, and project path are intact.
8. Exercise a failed or interrupted download in a disposable test copy if possible. The application must remain launchable, must not delete the database, and must report `error` locally.
9. If the installer is unsigned, record the SmartScreen warning as a release blocker rather than treating it as a test failure that can be ignored.

## Release decision

Do not publish `v1.4.0` until the real Windows test proves the entire path:

```text
v1.3.0 installed → manual Bootstrap install → newer release discovered
→ user-approved download → restart → new version running
→ userData, SQLite, Local Owner, settings, history, and project path intact
```

A successful Linux build, `latest.yml`, blockmap, or unit test is necessary but not sufficient evidence for this decision.
